# herdr starts an agent by agent start in its place's tab of its base's workspace, closes what it made once nothing live is in it, and finds a pane again by its agent's name

Status: accepted by the user, 2026-10-28, in their design session ("write 18"), on a trial of herdr 0.9.5's `agent start` against flume's herdr profile.

Deciders: the user, who chose `agent start`, that flume's agents run the program their settings name and no wrapper of the host's, and that herdr's workspaces are kept one per repository and base, never left behind, and carry display clues; the readings of herdr's answers, the bounds and the commands are the reviewing agent's.
Sources: `agentplot/blueprints:design/flume/requirements.md` at f44ec91, clauses 32, 34, 35, 38, 43, 46, 56, 64, 77, 94 to 98, 132, 135 to 139, C.4, C.5, S39 to S41 and S45 to S49, as amended with this record; records 0016 and 0017; rules core.10, core.12, core.29; herdr 0.9.5's own skill text (`herdr --skill`) and its `--help` for `agent start`, `pane split`, `tab create`, `tab close`, `workspace create`, `workspace close`, `pane report-metadata` and `workspace report-metadata`; a trial of herdr 0.9.5 on a server of its own on a scratch socket, 2026-10-28.

## Context and problem statement

Record 0016 had the herdr profile open a pane, type one line into its shell running a launcher file in the place's state folder, read the pane every 200 ms until the agent waited, look for the folder-trust question in the pane's visible text, and give the agent a herdr name for display only. Each of those is the profile guessing at something herdr 0.9.5 can now tell it.

A trial of herdr 0.9.5 on its own server found:

- `herdr agent start <name> --kind claude --pane <id> --timeout <ms> -- <arguments>` types the program's name into the pane's shell, so the shell's `PATH` and startup files apply, and hands it the arguments after `--` byte for byte: instructions of 6,000 and 20,000 characters with quotes, `$`, backticks and non-ASCII arrived whole. It answers `agent_started` with `interactive_ready: true` only once the program is ready; in a trusted folder Claude Code's SessionStart hook ran at 0.43 s and the start answered at 3.9 s.
- At the folder-trust question it answers at once, exit 1, `agent_not_ready` ("agent … is blocked during startup and is not ready for prompts"), and the agent stays `blocked` under its name. `agent send-keys <agent> down enter` and then `agent wait <agent> --until idle` came back idle in 0.3 s.
- It reads Claude Code's first run's theme picker and its sign-in choice as ready. A program that is missing, or ends while it starts, shows only as `timeout` ("timed out waiting for agent startup") once the whole bound has passed. Its other refusals are `agent_pane_busy` (the pane is not at a shell), `agent_name_taken`, `agent_pane_not_found` and `invalid_agent_timeout`; a kind it does not know exits 2 in plain text.
- `agent start` takes no environment and no directory. `pane split --cwd <dir> --env K=V`, and `tab create` and `workspace create` likewise, set what the program started in the pane sees: a `CLAUDE_CONFIG_DIR` so given reached Claude Code.
- The agent commands take the agent's name or its pane's id (`w1:p4`), never `<pane>@<socket>` or a terminal's id. A pane moved to another tab kept its id and its agent's name; moved to another workspace its id changed (`w1:p6` to `w2:p1`) and its agent's name went with it. A name leaves `agent list` when its program exits.
- `agent wait --until <state> --timeout <ms>` answers `timeout` past its bound; with no `--timeout` it waits for ever.
- A 70,000-character line through `pane run` ran, so the terminal's line limit record 0016 gave as the launcher file's reason was not met in the trial; herdr's skill text still says `pane run` and `agent start` refuse a line past the terminal's canonical input limit on macOS.

Record 0016 also said a pane is held by id and socket and a herdr name is for display only, since herdr drops a name whenever the pane's session changes. The trial shows the other half: a name follows its agent where the pane's id does not.

Two more asks came with the trial. `agent start --kind claude` types `claude`, so the shell picks the program; a host's `claude` wrapper that sets `CLAUDE_CONFIG_DIR` itself would override record 0017's environment, and the user is removing that wrapper from flume's runtime rather than asking every host to write one carefully. And Part C's one workspace labelled `flume` gathered every repository's places into one list, closed a place's pane but left its tab, and never closed anything, so workspaces and tabs lingered after their places had gone.

herdr 0.9.5 offers what both need: `tab close` and `workspace close`; `pane report-metadata <pane> --source <id>` with `--title` and `--display-agent`, and `workspace report-metadata <w> --source <id>` with `--token <name>=<value>`, a token the host's herdr sidebar rows show by `$<name>`; each display only.

## Considered options

1. Keep record 0016's open: a launcher file typed into the shell, the pane polled until the agent waits, the folder-trust question found in the screen.
2. herdr's agent start, in a pane made with the agent's environment, herdr's answers read as this record says, the pane found again by the agent's name; one workspace per repository and base and one tab per place, each closed once nothing live is in it; display clues at each settle.

## Decision outcome

Option 2.

1. **The open.** The profile makes the pane in the place, `--cwd <place>`, or splits beside a named pane, with an `--env` for each variable of the agent's environment: the environment resolved for it (record 0017) and flume's own `FLUME_*`. It then runs `herdr agent start <name> --kind <kind> --pane <id> --timeout 120000 -- <arguments>`, the call bounded at its timeout and ten seconds more (core.29). Nothing is typed into the pane's shell and no launcher file is written.
2. **A start held at a question.** `agent_not_ready` is the program's question before it starts. The profile reads the pane's visible lines: the folder-trust question alone is answered (34; record 0016), by `agent send-keys` with the keys the agent profile names, then `agent wait --until idle` under a bound of 30 seconds. Any other question, the warning about bypassing permissions or a sign-in among them, is never answered, and the start is never begun at once, delivered with the screen (35, 38, 43). This replaces record 0016's start that stays starting at such a dialog until the stage's limit, wherever the terminal can say the start is held; under a terminal that cannot, the printed command, that reading stands.
3. **herdr's ready is a second word.** The started ack from the agent's own SessionStart hook stays the start (35, 135; record 0016), since herdr reads a first run's setup screens as ready. herdr's `agent_started` sends no prompt by itself; flume still reads the screen. A `timeout` from `agent start` with no started ack is a start never begun, delivered with the pane's last lines.
4. **A pane is held by its id and socket, and found again by the agent's name.** The agent's herdr name is made from the identity, at most 32 of herdr's legal characters ending in a digest of the whole identity, so it is unique on the server; `agent_name_taken` refuses the open, as an agent already live under the identity (98). Where the pane's id no longer answers, as after a move to another workspace, `agent get <name>` finds the pane; it is taken as the agent's only once herdr lists it under that name, and its id is recorded before anything is sent to it. A role run's pane is its live start's and is found again the same way (132). A pane found by name and not checked is never sent to.
5. **The program the settings name, and a herdr kind per program.** The agent runs the program its settings name (record 0017's `program`, a name or a path), never a program a shell finds first. Since `agent start` types the kind's own name, the pane's `PATH` is led by a folder of the start's own holding that name linked to the program the settings name. Once herdr answers, the profile reads the program in the pane's foreground from `pane process-info` and the host's process table, by its path or, for a program a script starts, the script's path among its arguments; a start running anything else is closed and refused, naming what ran (32). No host needs a wrapper of any shape. `agent start` also needs a kind herdr knows. The agent profile names the program's kind with its command (C.4), `claude` for Claude Code, and the herdr profile takes only a kind the pinned herdr lists. A program herdr has no kind for cannot run under herdr, which refuses the launch naming it, as record 0017's refusal of a program the host's terminal cannot run says (32).
6. **One workspace per repository and base, one tab per place, and nothing left behind.** In the session the launch names, flume's own otherwise, the profile makes one workspace per repository and base, a bolt in crew's terms, labelled `<repository> <base>` (`flume bolt/the-surfaces`, `sluice main`), when the first place on that base opens, `--no-focus`; herdr 0.9.5 states no limit on a label, so it is kept whole. In it is one tab per place, `<kind>--<name>`, a unit of the bolt, whose panes are the place's agents, so a kind whose stage runs several agents at once splits its place's tab rather than needing a workspace of its own. A conversation's split beside a named pane stays where its caller put it. The profile records each workspace and tab it made, by id and server, in the host's state. When a place goes, by its tidy whether it landed or was dropped, its tab is closed, not only its pane (137); a workspace the profile made is closed once it holds no tab of a live place on its base and nothing it did not make, the last place on the base tidied or dropped. It never closes a workspace, tab or pane it did not make: a workspace where a person opened a pane is left open and status names it with what holds it. The terminal seam gains `tidy` (138) for this.
7. **Display clues.** At each settle that changes a stage's state, the profile reports `pane report-metadata <pane> --source flume --title "<stage> · <state>" --display-agent <kind>--<name>` and `workspace report-metadata <w> --source flume --token flume=<summary>`, the summary a one-line count of the places on the workspace's base running, asking, waiting on their caller and stalled. They are display only: nothing flume decides reads them back, and a report that fails is logged and never fails a settle. The terminal seam gains `show` (139), and the herdr plugin refreshes the same clues at each tick of its watch.
8. **Bounds.** Every `agent start` and `agent wait` call passes `--timeout`, since `agent wait` with none waits for ever (core.29). The start's 120 seconds leaves room for SessionStart hooks slow under load, which crew once read as a start never begun (record 0016); the trust answer's wait is 30 seconds, herdr's own default for a start.

### Consequences

- A pane's environment is not kept across a restart of herdr's server, and that is accepted: an agent herdr restores, or resumes bare, has no started ack for its start, so record 0016 already reads its stage lost and ends it once quiet (77); a retry opens a fresh pane with the environment set again. Before restarting herdr's server on purpose, the operator drains flume's places first.
- Amended 2026-10-29: panes run a shell that reads no startup files. On a host whose login shell rebuilds `PATH` (nix-darwin's `/etc/zshenv` and `/etc/profile`, macOS's path_helper, a user's rc file), the start's folder no longer led `PATH` once the pane's login shell had started, so `agent start`'s typed `claude` ran the shell's own: the check refused it, or, with no `claude` there, the start timed out. herdr 0.9.5 has no flag naming a pane's shell, and runs `$SHELL` from the pane's own environment (its `default_shell` setting, where a host's herdr configuration sets one, comes first). So the pane is made with `SHELL` a script in the start's folder that sets `SHELL` back to the user's and execs `zsh -f`, `bash --noprofile --norc`, or else `/bin/sh -i`, with `ENV` and `BASH_ENV` unset; and, since no startup file runs, its `--env` carries the host user's login environment, read once as the host reads it, under the agent's environment and flume's `PATH`. C.5 is amended to match at blueprints 480dbb4. The decision's fallback, taken by the orchestrating agent on a question the user had not yet answered; the user may revise it. The check after the start stands for what still slips past, a host's herdr `default_shell` or a program that runs another, and refuses naming what ran.
- The workspace clue shows only where the host's herdr sidebar rows name `$flume`; the pane's title shows wherever herdr shows a pane.
- herdr's skill text says `agent start` refuses a line past the terminal's canonical input limit on macOS; the trial's 20,000 characters of instructions passed. A start so refused is a refusal in herdr's words, and an instructions file read by the program is the answer should one be met.
- The statement's clauses 35 and 94, C.4, C.5 and scenarios S39 to S41 are amended, and clauses 137 to 139 and S45 to S49 added, at blueprints 7e324d4, ad5ffeb and f44ec91. Rule core.29's details gain `agent start`, its bounds and a clue that fails; core.10's the pane found again by name and the program the settings name; core.12's the start never begun at a question it does not answer; core.18's the tabs and workspaces closed. Record 0016 is amended: its launcher file, its one workspace and its herdr name for display only are this record's open, workspaces and name.
- The OpenSpec change `flume-runs-a-kind-through` carries it in group 9, reworking the open its group 7 built and adding `tidy` and `show`; `flume-runs-unattended-and-wakes-roles` carries the role run's pane found again by name in group 1 and the plugin's clues at each tick in group 6.
